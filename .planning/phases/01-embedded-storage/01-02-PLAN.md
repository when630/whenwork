**(1) `main/store.mjs` 신규.** `import { DatabaseSync } from 'node:sqlite'`로 시작하고, `main/queue.mjs`와 같은 팩토리 관례로 `export function createStore(file)`를 만든다. `DatabaseSync`는 동기 API이므로 `main/db.mjs`의 `async` 래핑은 걷어내고 전부 동기 함수로 쓴다(D-01이 요구하는 "같은 호출 흐름에서 즉시 반영"이 여기서 자연스러워진다).

`MIGRATIONS`는 모듈 최상단의 배열이고 각 원소는 `(db) => db.exec(...)` 함수다. 첫 원소(v1)가 만드는 것:
- `project` — `id INTEGER PRIMARY KEY AUTOINCREMENT`, `name TEXT NOT NULL UNIQUE`, `abbr TEXT`, `status TEXT NOT NULL DEFAULT 'active'`, `sort INTEGER NOT NULL DEFAULT 0`
- `item` — `id TEXT PRIMARY KEY`, `project_id INTEGER REFERENCES project(id)`, `kind TEXT NOT NULL DEFAULT 'inbox' CHECK (kind IN ('inbox','todo','waiting'))`, `title TEXT NOT NULL`, `due TEXT`, `waiting_for TEXT`, `captured_at TEXT NOT NULL`, `done_at TEXT`, `source TEXT NOT NULL DEFAULT 'manual'`, `context TEXT`, `note TEXT`, `nudged_at TEXT`, `nudge_count INTEGER NOT NULL DEFAULT 0`, `deleted_at TEXT`
- `event` — `id INTEGER PRIMARY KEY AUTOINCREMENT`, `at TEXT NOT NULL`, `kind TEXT NOT NULL`, `detail TEXT`
- 인덱스와 외래키 강제 여부 — **Task 1에서 확정한 선택을 그대로 따른다**. 최소안은 `item(due)`, `item(kind)`, `event(at DESC)` 세 개다

세 테이블이 전부다. STOR-05가 금지한 테이블 이름(REQUIREMENTS.md STOR-05와 `main/db.mjs`의 현재 SCHEMA에 목록이 있다)은 `main/store.mjs` 어디에도 등장하지 않아야 한다. D-11이 뺀 칼럼(AI 분류 제안·이슈 URL·완료 제안 3종·프로젝트 리포 경로)도 만들지 않는다. `item.context`는 과거 값 이전용으로 TEXT(JSON 직렬화)로 남긴다.

시각 칼럼은 전부 TEXT다 — 쓸 때 `new Date().toISOString()`, `due`만 `YYYY-MM-DD` 문자열(D-10). SQL 안에서 시간을 계산하지 않는다: "N시간 전/N일 전" 같은 경계는 호출부 JS에서 `Date`로 계산해 문자열 파라미터로 바인딩하고, SQL은 `<`/`>` 문자열 비교만 한다(RESEARCH `Pattern 3`, `SQL 변환 표`). PostgreSQL 전용 시간 연산자와 캐스트는 `main/store.mjs`에 한 글자도 남기지 않는다.

**(2) 열기·프라그마·마이그레이션.** `open()`은 `new DatabaseSync(file)` 뒤 순서대로 `PRAGMA journal_mode = WAL`과 `PRAGMA synchronous = FULL`을 `exec`로 건다(D-17). `PRAGMA foreign_keys`는 Task 1의 결정을 따른다. PRAGMA 값은 파라미터 바인딩을 받지 않으므로 템플릿 리터럴로 직접 넣는다(RESEARCH Pitfall 4) — 넣는 값은 전부 내부 계산 상수·정수이고 사용자 입력이 아니다.

`migrate(db)`: `PRAGMA user_version`을 읽어 현재 버전 `current`를 얻고, `current`가 `MIGRATIONS.length`보다 크면 `NewerSchemaError`를 던진다(D-13 — 처리는 Task 3). 아니면 `current`부터 끝까지 각 마이그레이션을 `BEGIN`/`COMMIT`으로 감싸 적용하고 같은 트랜잭션에서 `user_version`을 올린다. 실패하면 `ROLLBACK` 후 그대로 던진다. `node:sqlite`에는 트랜잭션 헬퍼가 없으므로 `withTransaction(db, fn)` 세 줄짜리 내부 헬퍼를 직접 둔다(RESEARCH `Pattern 2` 주의 문단).

`status()`는 위 인터페이스 계약대로 `{ ok, reason, notice, quarantined }`를 돌려준다. 이 작업(Task 2) 범위에서는 정상 열림(`{ ok: true, reason: null, notice: null, quarantined: null }`)과 예외 시 `{ ok: false, reason: 'error', notice: '저장소를 열지 못했습니다 — 캡처는 로컬 큐에 안전하게 쌓입니다', quarantined: null }`만 채우면 된다. 손상·상위버전 분기는 Task 3이 채운다. `reopen()`은 `close()` 후 `open()`이다(D-03이 쓸 재시도 경로).

`checkpoint()`는 `PRAGMA wal_checkpoint(TRUNCATE)`를 실행하고 실패는 조용히 삼킨다. `close()`는 `checkpoint()` 후 핸들을 닫는다(D-17 — 사용자가 `store.sqlite` 하나만 복사해도 온전해야 한다).
